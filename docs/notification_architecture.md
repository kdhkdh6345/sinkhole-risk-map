# 싱크홀 위험지도 알림 전파 통신 네트워크 아키텍처

본 문서는 싱크홀 위험지도의 3단계(위험) 경보 발생 시, 해당 지역의 시민과 유관 기관 담당자에게 신속하고 정확하게 알림을 전파하기 위한 통신 네트워크 아키텍처 설계 및 구현 방안을 정의합니다. 

이 설계는 **"누구에게, 어떻게, 가장 빨리 알릴 것인가"**라는 핵심 요구사항을 정보통신공학적 관점(지오펜싱 필터링, MQTT 통신, 브로드캐스트 채널 선정)에서 풀어낸 결과물입니다.

---

## 1. 지오펜싱(Geofencing) 기반 메시지 브로드캐스트 설계
전 서울 시민에게 무분별한 알림이 발송되는 것을 방지하고, 실제 위험 반경에 존재하는 사용자에게만 선택적으로 경보를 전송하기 위해 공간 필터링을 적용합니다.

### 1.1 설계 구조
- **위험 격자 식별:** 실시간 스냅샷에서 `stage=3`으로 판정된 500m×500m 격자의 중심 좌표(위/경도) 추출.
- **반경 설정 (Geofence):** 격자 중심을 기준으로 반경 500m (또는 1km) 영역을 `Polygon` 또는 `Radial 펜스` 형태로 정의.
- **공간 쿼리 (Spatial Query):** Redis Geo 또는 PostGIS를 활용하여 현재 해당 펜스 내부에 GPS 좌표가 존재하는 활성 디바이스 토큰(Device Token)을 추출.
- **전송:** 추출된 토큰들에 대해서만 알림(Push) 브로드캐스트 수행.

### 1.2 통신공학적 이점
불필요한 트래픽 낭비를 줄이고, 코어 네트워크의 부하를 획기적으로 낮춥니다. (Spatial Filtering을 통한 백엔드 라우팅 최적화)

---

## 2. MQTT Pub/Sub 아키텍처 기반 실시간 전파

다수의 디바이스에 지연 없이 즉각적으로 경보를 푸시하기 위해 경량 IoT 프로토콜인 **MQTT (Message Queuing Telemetry Transport)** 아키텍처를 도입합니다. HTTP 폴링(Polling) 대비 연결 유지 비용(Overhead)이 현저히 낮고 배터리 효율이 높습니다.

### 2.1 아키텍처 다이어그램 (개념도)
```mermaid
graph LR
    A[위험도 판정 서버] -->|Publish (위험 알림)| B(MQTT Broker)
    B -->|Subscribe (Topic: seoul/dobong/warn)| C[시민 App 1]
    B -->|Subscribe (Topic: seoul/dobong/warn)| D[시민 App 2]
    B -->|Subscribe (Topic: seoul/admin)| E[담당자 관제 시스템]
```

### 2.2 QoS (Quality of Service) 레벨 설정
- **시민 대상 알림 (Topic: `seoul/{gu}/warn`):** **QoS 1 (At least once)**
  - 재난 알림의 특성상 반드시 한 번은 전달되어야 함. 중복 수신이 발생하더라도 미수신(Loss)보다 낫기 때문에, Broker와 Client 간의 PUBACK 확인(ACK)을 거침.
- **담당자 관제망 (Topic: `seoul/admin`):** **QoS 2 (Exactly once)**
  - 관제 시스템에서는 알림 중복 시 2차 자동화 시스템(예: 교통 통제 로직)의 오작동 우려가 있으므로, 약간의 지연(4단계 Handshake)이 추가되더라도 정확히 한 번만 도달하도록 보장함.

## 3. 상황별 알림 채널 비교 및 폴백(Fallback) 전략

위험도나 긴급성에 따라 알림 채널을 차등적으로 운영하여 효율을 극대화합니다. 앱이 설치되지 않은 사용자에게도 도달할 수 있는 **긴급재난문자(CBS)**와 정밀 타겟팅이 가능한 **앱 푸시(FCM)**를 혼합하여 사용합니다.

| 구분 | 긴급재난문자 (CBS) | 앱 푸시 (FCM / APNs) |
| :--- | :--- | :--- |
| **통신 방식** | 기지국 브로드캐스트 (Cell Broadcast) | IP 네트워크 기반 유니캐스트/멀티캐스트 |
| **전송 지연 (Latency)** | 수 초 이내 (빠름) | 수 초 ~ 수 분 (네트워크 상태/절전모드 의존) |
| **도달률 (Reliability)** | 해당 기지국 반경 내 모든 기기(100% 근접) | 앱 설치 및 알림 수신 동의자만 수신 |
| **타겟팅 정밀도** | 기지국 셀(Cell) 단위 (수 km) - 정밀도 낮음 | 사용자 GPS 좌표 기준 지오펜싱 - 정밀도 높음 (수십 m) |
| **권장 사용 시나리오** | **1시간 누적 72mm 이상 등 대형 함몰 직전의 극한(Extreme) 상황** | **2단계(주의) 및 국지적(500m 격자) 싱크홀 전조 현상 탐지 시** |

### 3.1 Fallback 로직
1. **Primary (App Push):** 지오펜스 내 사용자에게 FCM을 통한 즉각 푸시 (위치 정확도 높음).
2. **Secondary (CBS):** 만약 `stage=3` 상태가 3시간 이상 지속되거나, 기상청 호우경보 데이터와 결합되어 '극한 호우'로 식별된 경우 통신사를 통해 해당 구역 기지국 CBS 송출 요청.

---
> **[작성자 요약]**
> 위 아키텍처는 "단순히 앱 푸시를 보낸다"를 넘어, 공학적 관점에서의 데이터 분배(MQTT Pub/Sub), 네트워크 부하 저감(Geofencing), 품질 보장(QoS), 통신매체 특성(CBS vs IP Push) 분석이 반영된 완성도 높은 전파 체계입니다.
