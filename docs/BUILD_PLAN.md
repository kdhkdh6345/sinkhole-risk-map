# BUILD_PLAN.md — 단계별 작업 명세

`AGENTS.md`의 규칙을 전제로 한다. Phase는 순서대로 진행하며, 수용 기준을 통과하지 못하면 다음 단계로 넘어가지 않는다.

각 Phase 끝의 **[지시 프롬프트]** 는 Antigravity 에이전트에게 그대로 붙여넣어 사용한다.

---

## Phase 0 — 저장소 골격

**목표**: 디렉터리 구조와 설정 파일을 만들고, 빈 파이프라인이 에러 없이 실행되게 한다.

**산출물**
- `AGENTS.md`의 4절 구조대로 디렉터리·`__init__.py` 생성
- `config/grid.yaml`, `config/weights.yaml` (6절 값 반영)
- `requirements.txt`, `.gitignore` (`.env`, `data/*.parquet`, `__pycache__` 포함)
- `src/sinkhole/core/clock.py` — `RealClock`, `AcceleratedClock(speed)` 두 구현
- `pytest` 실행 가능 상태

**수용 기준**
1. `pytest`가 0개 실패로 통과한다.
2. `AcceleratedClock(speed=3600)`에서 실시간 1초 경과 시 `now()`가 약 3600초 증가한다 (테스트 코드로 검증).
3. `python -c "import yaml; yaml.safe_load(open('config/weights.yaml'))"`가 성공하고, 정적 배점 합이 60, 실시간 배점 합이 40이다.

**[지시 프롬프트]**
> AGENTS.md와 docs/BUILD_PLAN.md를 읽고 Phase 0을 진행해줘. 구현 계획을 먼저 보여주고 승인받은 뒤 코드를 작성해. 완료 후 수용 기준 3개를 실제로 실행해서 결과를 보여줘.

## Phase 1 — 격자 생성

**목표**: 서울시를 500m 격자로 나누고, 이후 모든 단계가 참조할 불변 격자 파일을 만든다.

**입력**: 서울시 행정경계 shapefile 또는 GeoJSON (사용자가 `data/raw/`에 제공)

**작업**
1. bounding box(위도 37.413~37.715, 경도 126.764~127.184)를 500m 간격 격자 중심점으로 분할
2. geopandas로 서울시 행정경계와 교차 판정하여 **경계 밖 격자 제거**
3. 각 격자에 자치구명 부여
4. `data/grid.parquet` 저장 (컬럼: `id`, `lat`, `lon`, `gu`). `id`는 0부터 연속
5. `web/data/grid.json`으로 내보내기

**수용 기준**
1. 격자 수가 2,300~2,600개 범위다. (bbox 기준 약 5,000개에서 절반가량 제거되어야 정상)
2. `id`가 0부터 빈 번호 없이 연속한다.
3. 자치구가 25개 모두 등장하고, 어떤 격자도 `gu`가 비어 있지 않다.
4. `grid.json` 파일 크기가 500KB 미만이다.
5. 스크립트를 두 번 실행해도 `grid.parquet`의 내용이 동일하다.

**[지시 프롬프트]**
> Phase 1을 진행해줘. data/raw/에 있는 서울시 행정경계 파일을 사용해. 완료 후 수용 기준 5개를 검증하고, 격자 수와 자치구별 격자 개수 표를 출력해줘.

## Phase 2 — 정적 기저점수 B

**목표**: 실시간 데이터 없이도 지도가 뜨는 상태를 만든다.

**작업**
1. `static_layers/sewer.py` — 자치구별 하수관 노후 비율(30년/50년 이상)을 0~20점으로 정규화
2. 나머지 세 레이어(`borehole.py`, `history.py`, `liquefaction.py`)는 **인터페이스만 먼저 구현하고 0점을 반환**한다. 데이터 확보 후 채운다.
3. `baseline.py`에서 네 레이어를 가중합해 `data/baseline.npy` 저장 (길이 N)
4. 점수 분포 히스토그램을 `docs/tuning.md`에 기록

**수용 기준**
1. `baseline.npy` 길이가 격자 수와 정확히 일치한다.
2. 모든 값이 0 이상 60 이하다.
3. 같은 자치구의 격자들이 하수관 항목에서 동일한 값을 받는다 (자치구 단위 데이터이므로 정상 동작).
4. 점수 분포의 백분위수(10/25/50/75/90)를 출력하고, `B >= 30` 기준으로 몇 %의 격자가 1단계에 해당하는지 보고한다.

> **주의**: 4번 결과가 90% 이상이거나 5% 미만이면 임계값이 잘못된 것이다. 코드를 고치지 말고 사용자에게 보고한다.

**[지시 프롬프트]**
> Phase 2를 진행해줘. 하수관 노후도만 실제 데이터로 구현하고 나머지 세 레이어는 0을 반환하는 스텁으로 두되, 인터페이스는 나중에 채울 수 있게 완성해줘. 완료 후 점수 분포 백분위수를 출력해줘.

## Phase 3 — 시뮬레이션 어댑터 + 계산 엔진

**목표**: 실제 API 없이 전체 파이프라인을 끝에서 끝까지 관통시킨다. **이 단계가 프로젝트의 핵심이다.**

**작업**
1. `sources/base.py` — 추상 클래스 `SourceAdapter`. 메서드는 `fetch(grid) -> np.ndarray` 하나
2. `sources/simulated.py` — 세 채널의 시나리오 생성기
   - `scenario="calm"` — 평시. 대부분 1단계
   - `scenario="heavy_rain"` — 특정 자치구에 호우경보급 강수 집중
   - `scenario="extreme"` — 극한호우 + 지하수위 2σ 급락
3. `fusion/decay.py` — 감쇠 함수 (세 채널 공용, numpy 벡터 연산)
4. `fusion/scoring.py` — R/G/T 점수화 + 단계 판정
5. `core/field.py` — `GridRiskField`. 상태를 numpy 배열 세트로 관리
6. `core/store.py` — `state.npz` 스냅샷 저장·복원
7. `scripts/run_snapshot.py --mode sim --scenario heavy_rain` → `web/data/snapshot.json` 생성

**수용 기준**
1. `--scenario calm`에서 3단계 격자가 0개다.
2. `--scenario extreme`에서 3단계 격자가 1개 이상 존재한다.
3. `AcceleratedClock`으로 96시간을 가속 경과시켰을 때, 특정 격자의 `r` 값이 다음을 만족한다.
   - 0~24시간: 최초값 유지 (오차 1% 이내)
   - 48시간 시점: 최초값의 약 0.22배
   - 72시간 시점: 최초값의 약 0.05배
   - 72시간 초과: 0
4. `G >= 10`이어도 `R < 15`이면 3단계로 격상되지 않는다 (누적 조건 검증 테스트).
5. 프로세스를 종료 후 재시작해도 `state.npz`에서 감쇠 진행 상태가 복원된다.
6. 생성된 `snapshot.json`이 AGENTS.md 5.2절 스키마와 정확히 일치한다.
7. 격자 2,400개 기준 1회 계산이 1초 미만이다.

**[지시 프롬프트]**
> Phase 3을 진행해줘. 이번 단계에서는 실제 API를 전혀 호출하지 않고 시뮬레이션 어댑터로만 전체 파이프라인을 완성해. 수용 기준 3번(감쇠 곡선)과 4번(누적 조건)은 반드시 pytest 테스트 코드로 작성해서 실행 결과를 보여줘.

## Phase 4 — 웹 지도 (정적)

**목표**: 링크 하나로 공유 가능한 지도를 만든다. 서버 없이 동작해야 한다.

**작업**
1. `web/index.html` — Leaflet 지도 + 서울시 초기 뷰
2. `web/js/render.js` — `grid.json` + `snapshot.json`을 조인해 격자를 사각형으로 렌더링. 1/2/3단계를 초록·노랑·빨강으로 채색
3. 격자 클릭 시 팝업: 총점, 단계, **b/r/g/t 항목별 분해**, 불확실성
4. 헤더에 `generated_at` 표시. 20분 이상 경과 시 "갱신 지연" 배지
5. 범례, 단계별 격자 개수 카운터
6. `web/js/sim.js` — 브라우저 내 시뮬레이션 엔진. Python의 감쇠·점수화 로직을 JS로 이식
   - 강수량 슬라이더, 시나리오 선택, 시간 가속 재생 버튼
   - 서버 통신 없이 동작

**수용 기준**
1. `web/` 디렉터리를 `python -m http.server`로 열었을 때 지도가 정상 표시된다.
2. 네트워크를 끊어도 시뮬레이션 모드가 동작한다 (외부 호출은 Leaflet CDN과 타일뿐).
3. 시간 가속 재생 시 72시간 경과 후 모든 격자가 1단계로 복귀한다.
4. **JS 시뮬 결과와 Python 결과가 일치한다.** 동일 입력·동일 시각에서 점수 차이가 0.01 미만임을 확인한다. (검증용 고정 입력 케이스를 `tests/fixtures/parity.json`에 두고 양쪽으로 실행)
5. 저장소 어느 파일에도 API 키가 없다 (`grep -ri "serviceKey\|api_key\|authKey" web/` 결과 없음).
6. 모바일 화면 폭 375px에서 지도와 범례가 겹치지 않는다.

> 4번은 특히 중요하다. 두 구현이 갈라지면 시연에서 "실시간 지도와 시뮬 지도가 다른 답을 내는" 상황이 발생한다.

**[지시 프롬프트]**
> Phase 4를 진행해줘. 프레임워크나 번들러 없이 순수 HTML/CSS/JS로만 만들어. 수용 기준 4번(Python-JS 일치 검증)은 반드시 실제로 양쪽을 실행해서 수치를 비교해 보여줘.

## Phase 5 — GitHub Pages 배포 + 자동 갱신

**목표**: 외부인이 링크로 접속 가능하게 만든다.

**작업**
1. GitHub Pages를 `web/` 기준으로 설정 (또는 `docs/`로 경로 조정)
2. `.github/workflows/snapshot.yml`
   - `schedule: cron` 5~10분 주기 + `workflow_dispatch` 수동 실행
   - Python 환경 구성 → `run_snapshot.py --mode real` 실행
   - 성공 시에만 `web/data/snapshot.json` 커밋 & 푸시
   - **실패 시 기존 파일을 건드리지 않고 워크플로만 실패 처리**
3. API 키는 `secrets.KMA_API_KEY` 등으로 주입
4. `README.md` — 프로젝트 소개, 배포 URL, 로컬 실행법

**수용 기준**
1. `workflow_dispatch`로 수동 실행 시 `snapshot.json`이 갱신되고 커밋된다.
2. 의도적으로 API 키를 비웠을 때 워크플로가 실패하되 기존 `snapshot.json`은 그대로 유지된다.
3. 배포된 공개 URL에서 지도가 정상 표시된다.
4. 커밋 이력에 API 키가 남아 있지 않다.

**[지시 프롬프트]**
> Phase 5를 진행해줘. Actions 워크플로는 실패 시 기존 스냅샷을 절대 덮어쓰지 않도록 작성해. API 키는 Secrets에서만 읽고, 로그에 출력되지 않게 해줘.

## Phase 6 — 실제 API 연동

**목표**: 시뮬 어댑터를 실제 API 어댑터로 교체한다. **엔진 코드는 한 줄도 고치지 않는다.**

순서대로 하나씩 진행하며, 각각을 별도 Phase처럼 취급한다.

### 6-1. 기상청 API허브 (강수)
- 500m 격자 NetCDF4 응답을 파싱해 격자 배열로 변환
- 1h/3h/12h 누적을 계산해 R 점수 구간에 매핑
- 응답 샘플을 `data/fixtures/kma_sample.nc`에 저장하고, 테스트는 이 파일로 수행

### 6-2. GIMS / 서울시 보조지하수 관측망 (지하수위)
- 관측정 단위로 최근 30일 이력을 SQLite에 누적 (σ 계산에 필요)
- 관측정별 σ 계산 → 최근접 또는 IDW 보간으로 격자 투영
- 2회 연속 유지 조건 구현

### 6-3. 교통 (선택)
- 기본은 정적 프록시. TOPIS 연동은 여유가 있을 때만
- 링크 시점·종점 좌표 → 격자 매핑 → 길이 가중평균

**공통 수용 기준**
1. 어댑터 교체만으로 동작하며, `fusion/`, `core/` 코드가 변경되지 않았다 (`git diff`로 확인).
2. API 실패·타임아웃 시 해당 채널만 `np.nan`이 되고, 나머지 채널로 계산이 계속된다.
3. `snapshot.json`의 `source_status`에 채널별 상태가 정확히 기록된다.
4. 응답 파싱 결과가 fixture 기반 테스트를 통과한다.

**[지시 프롬프트]**
> Phase 6-1(기상청 강수)만 진행해줘. fusion/과 core/ 디렉터리는 절대 수정하지 말고, sources/kma.py만 구현해. 완료 후 git diff로 다른 디렉터리가 변경되지 않았음을 보여줘.

## Phase 7 — 전공 심화 (학술제 차별화 요소)

여기부터는 기능이 아니라 **평가 점수를 위한 항목**이다. 앞 단계가 모두 동작한 뒤 착수한다.

### 7-1. 다중센서 융합 (칼만/베이지안)
- 각 소스에 측정 분산을 부여한다 (액상화=작음, 지하수위 보간=큼)
- 해상도·신뢰도가 다른 값들을 통계적으로 결합해 격자별 최적 추정치와 **불확실성(신뢰구간)** 을 함께 산출
- `snapshot.json`의 `unc` 필드를 실제 값으로 채운다
- **비교 실험 필수**: 단순 가중합 대비 개선 정도를 표로 정리해 `docs/fusion_eval.md`에 기록. 이 표가 보고서의 핵심 증거다

### 7-2. 예측 잔차 기반 이상탐지
- "1σ 넘으면 이상" 규칙을 **상태공간 모델 기반 예측 → 잔차 판정**으로 교체
- 다음 시점 지하수위를 예측하고, 실측과의 잔차가 크면 이상으로 판정
- 규칙기반 대비 오탐률 비교를 기록

### 7-3. 알림 전파 아키텍처 (문서로 충분)
- 지오펜싱 기반 선택적 브로드캐스트 설계
- MQTT Pub/Sub 토픽 구조와 QoS 레벨 선택 근거
- 재난문자(CBS) vs 앱 푸시(FCM) 지연시간·도달률 비교표
- `docs/notification_architecture.md` + 아키텍처 다이어그램

**수용 기준**
1. 융합 적용 전후 비교표가 실제 수치로 존재한다.
2. `unc` 값이 데이터가 희소한 격자에서 더 크게 나온다 (직관과 일치하는지 검증).
3. 이상탐지 교체 후에도 Phase 3의 감쇠·단계판정 테스트가 여전히 통과한다.

**[지시 프롬프트]**
> Phase 7-1을 진행해줘. 기존 단순 가중합 경로는 지우지 말고 옵션으로 남겨둬서, 두 방식의 결과를 같은 입력으로 비교할 수 있게 해줘. 비교표를 docs/fusion_eval.md에 만들어줘.
